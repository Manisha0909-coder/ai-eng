# Retrieval Ablation

Generated by `python -m eval.run_ablation` against the 120-example golden
dataset (98 answerable), chunk-level, no LLM calls. See
`eval/ablation_report.json` for the raw numbers this file summarizes.

## Why chunk-level, not document-level

The old (52-example, 4-document) ablation only checked whether the right
*document* showed up in the top-k. On a 24-document corpus with
deliberately overlapping topics, that's too generous: a question can
retrieve the right document's wrong chunk, or a competing document that
happens to also mention the right keyword. `expected_chunk_substring`
checks whether the chunk that actually contains the answer was retrieved,
not just the right document.

## Honest reading

- **Reranking now visibly earns its place.** At k=3 (the production
  `FINAL_TOP_K`), hybrid+rerank beats hybrid RRF alone on both splits
  (dev: 0.74 vs 0.66; test: 0.896 vs 0.833) — a real, measurable lift,
  unlike the old 4-document corpus where RRF alone already got
  everything right and reranking had nothing left to improve. A bigger,
  harder corpus with genuine near-miss documents is what surfaces this.
- **Vector-only is still a strong baseline** and occasionally edges out
  hybrid on raw MRR (dev: 0.867 vs 0.800) — BM25's crude tokenizer
  (`rag/retrieval.py`) sometimes pulls in a lexically-similar wrong
  document (e.g. a different policy that happens to share a number),
  dragging hybrid's rank-fusion down slightly. This is a real trade-off,
  not a bug: BM25 still clearly helps at k=5 and in the ablation's
  "doc found by both retrievers outranks found by only one" property
  (see `tests/test_retrieval.py`), it's just not uniformly better on
  every metric on this specific dataset.
- **Chunk size 400 trades hit-rate for MRR**: slightly worse at finding
  the right chunk at all (0.796 vs 0.816), but when it does find it,
  ranks it better on average (MRR 0.827 vs 0.802) — larger chunks carry
  more context per chunk (helping rank), but also blur section
  boundaries more (hurting precision on which specific chunk is "the"
  answer). 200 remains the better default for this corpus.
- **dev vs test numbers differ** (e.g. hybrid+rerank k=3 hit rate: 0.74
  dev vs 0.896 test) because the stratified split, while balanced per
  category, didn't balance *difficulty* within each category — a known
  limitation of a random (seeded) split on a dataset this small. Don't
  read the gap as dev/test leakage; read it as sampling noise on ~50
  examples per split, worth revisiting if the dataset grows.
